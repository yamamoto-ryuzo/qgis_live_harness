コンポーネント 1

QGIS Live Driver

Harnessから独立した汎用制御プラグイン — QGIS側の「手」。

qgis-plugin/qgis_live_driver/ は UIを持たない制御専用プラグインで、実行中QGISを外部から遠隔操作する面を提供する。 QWebEngineView を持たないため、WebEngineを使わない任意のQGIS環境・ 任意の他プラグインに対しても使える汎用部品。

pyeval でQGISプロセス内の任意Pythonを同期実行できるため、 PyQGISで書ける操作は全て制御可能: レイヤー/プロジェクト操作、 キャンバス、メニュー/アクション、qgis.utils.plugins 経由の他プラグイン、 Processing、QgsSettings、任意widgetの grab() による画像化 等。

さらに status/open_plugin/reload_plugin/bridge_call のnamedコマンドと、 plugin_id による他プラグインへのコマンド転送(ハブ機能)を持つ。

コマンド

コマンド 動作
pyeval QGISプロセス内で任意Pythonを同期実行し結果を返す。名前空間に iface / QgsProject / QgsApplication / driver を持つ → iface.activeLayer().name() や QgsProject.instance().mapLayers() 等で内部状態を直接取得・操作できる
screenshot iface.mapCanvas().saveAsImage(path) で地図キャンバスをPNG保存。target:"mainwindow" でQGISメインウィンドウを grab()
status pid / http_port / live_dir / ロード中プラグインと各driver・view有無を返す(生存確認・一覧用)
open_plugin plugin_id のプラグインをload+startし、open_dialog があれば開く
reload_plugin plugin_id のプラグインを sys.modules 掃除+reloadPlugin+open_dialog でホットリロード(QGIS再起動不要。自プラグイン自身も可)
bridge_call plugin_id + method + args で対象プラグインのbridgeオブジェクトをプロセス内で直接呼ぶ。WebChannelを通らないためJSレンダラー飢餓中でも動作する。JSON文字列の返値はパースして返す
eval / devreload viewを持たないため unsupported エラーを返す(ハングしない)。ただし plugin_id を付けると対象プラグインへ転送される(下記)

plugin_idルーティング(ハブ機能)

eval / pyeval / screenshot / devreload に plugin_id を付けると、 そのプラグインのLiveDriver(plugin.driver/plugin._live)へコマンドが 転送され、結果は呼び出し元の results.jsonl に返る。 つまりこのドライバのlive dir / HTTPポート1本で全プラグインを制御できる。

  • 転送先ドライバは _handle(cmd, reply) の reply 引数に対応している必要がある(repo同梱の webengine_plugin 版 live_driver.py は対応済み)
  • pyeval を転送すると対象プラグインの名前空間(その view/driver)で実行される

制御可能な範囲(pyeval)

対象 pyevalの例
レイヤー/プロジェクト iface.addVectorLayer(...) / QgsProject.instance().write()
キャンバス iface.mapCanvas().setExtent(...) / .refresh()
メニュー/ツールバー iface.actionZoomIn().trigger()、mainWindow().findChildren(QAction) で全アクション列挙・実行
他プラグイン qgis.utils.plugins["<id>"] で他プラグインのオブジェクトに到達
Processing processing.run("native:buffer", {...})
設定 QgsSettings().setValue(...)
任意ウィジェットの画像化 widget.grab().save(path)(pyeval経由)

制約:

  • 同期GUIスレッド実行 — pyeval実行中はGUIがブロックし、逆に再描画等でGUIビジーの間はポーリングが飢餓する(一時的)
  • OSネイティブダイアログ — Qt外のダイアログはwidget introspection経由の間接操作。Qtモーダルは QApplication.activeModalWidget() で accept()/reject() 可能
  • 実マウス/実キー — QMouseEvent/QTest.mouseClick のpostで模倣可能だが座標変換等の下ごしらえが必要
  • Python API未露出の内部機能 — 稀だがC++ privateな振る舞いは不可

接続面(4系統・全て同じdispatchへ)

  • ファイルJSONL — commands.jsonl 追記 → QTimerが実行 → results.jsonl 返却。 言語非依存の最下位輸送層
  • HTTP REST — POST 127.0.0.1:<port>/api/pyeval {"code":"..."} 等。 MCPを知らないfunction calling系AI・curl・自作エージェント向け
  • MCP Streamable HTTP — POST 127.0.0.1:<port>/mcp(JSON-RPC)
  • MCP stdio — 同梱 mcp_stdio.py をspawnするだけ(stdlibのみ、spawn側にQGIS/Node不要)

②③はプラグイン内蔵の http.server(stdlibのみ・127.0.0.1・空きポート自動選択)が提供。 ワーカースレッドが受けた命令は driver.submit() でメモリキューに入り、 GUIスレッドのQTimerがファイルJSONLと同じ要領で実行する(dispatchは1本に統一)。 ポート番号等の接続情報は ~/.qgis-live/<pid>-qgis_live_driver.json に書き出され、 クライアントはここから自動検出できる(QGIS_LIVE_REGISTRYで変更可)。

HTTP RESTエンドポイント

エンドポイント 内容
GET /api/health {"ok":true,"pid":...,"plugin":"qgis_live_driver"}
GET /api/tools ツール仕様JSON(function calling系AIが読む用)
GET /api/status status コマンドの結果
POST /api/cmd コマンドJSONをそのままdispatch({"type":"reload_plugin","plugin_id":"..."} 等すべて有効)
POST /api/pyeval {"code":"...", "plugin_id":"..."} → {"result":...}
POST /api/eval {"expression":"...", "plugin_id":"<id>"} → 対象プラグインへ転送(plugin_id無しなら unsupported)
POST /api/screenshot {"path":"...","plugin_id":"...","target":"..."} → PNGバイナリ(Content-Type: image/png)
POST /mcp MCP JSON-RPC (initialize/tools/list/tools/call/ping)

MCP tools は qgis_<コマンド種別> の命名で、引数はコマンドJSONの キーにそのまま対応する(plugin_id / target / method / args 等)。

ファイルプロトコル詳細

環境変数 WEBENGINE_LIVE_DIR が設定された状態でQGISが起動すると、 initGui 時に live_driver.py が起動し WEBENGINE_LIVE_DIR/qgis-<pid>/qgis_live_driver/ をポーリングする:

外部アプリ → commands.jsonl に1行1JSONを追記
           → QTimer(200ms)が読み取り実行
           → results.jsonl に {id, result|error} を追記で返却
  • 輸送層はファイルのみ。言語非依存(JSON Linesを追記・読取できれば何でもよい)
  • commands.jsonl は append-only。切り詰めるとドライバのoffsetがずれてmid-line読み(JSONDecodeError+コマンド喪失)を起こす
  • 同一live dirへの同時アクセスは 単一クライアント 前提

外部公開(Copilot Studio等からの接続)

/mcp は Copilot Studio が対応する Streamable HTTP transport 互換だが、 既定では 127.0.0.1・認証なしのためクラウドからは到達しない。 以下の手順で公開できる。

1. APIキー認証と公開ツールの絞り込み(QGIS起動前にenvを設定)

$env:QGIS_LIVE_API_KEY = "<ランダムなキー>"
# 推奨: 公開ツールを限定。pyevalは任意コード実行のため除外
$env:QGIS_LIVE_TOOLS = "status,screenshot"
npm run live:ensure
  • 親シェルのenvは live:ensure → powershell → Start-Process 経由でQGISへ引き継がれる。既にQGISがlive中の場合は再起動が必要(envは起動時に読む)
  • QGIS_LIVE_API_KEY 設定時は Authorization: Bearer <key> / X-Api-Key: / api-key: のいずれかのヘッダを要求(不一致は401)。/api/health のみ無認証
  • QGIS_LIVE_TOOLS はコマンド種別名のカンマ区切り(qgis_前置も可、*または未設定で全許可)。/mcp の tools/list・tools/call と /api/* の両方に効く
  • 有効状態は ~/.qgis-live/<pid>-qgis_live_driver.json の http_auth / http_tools / mcp_url で確認できる(キー自体は書き出さない)

2. HTTPSで公開(トンネル)

Copilot Studioはクラウドのため公開URLが必要。ローカルポートをトンネルする:

devtunnel host -p <port> --allow-anonymous
# または
ngrok http <port>

(TLS終端とFQDN払い出しはトンネル側が担い、認証は /mcp 側のAPIキーが担う)

3. Copilot Studio 側の設定

エージェントの Tools → Add a tool → New tool → Model Context Protocol で MCP onboarding wizardを開き、Server URL に https://<トンネルFQDN>/mcp、 認証に API key を選んで QGIS_LIVE_API_KEY の値を入力する。 generative orchestration が有効なエージェントが必要。 追加後は qgis_status 等がツールとして使える。

REST面を使う場合は Power Apps カスタムコネクタ経由で /api/* を包む方法もある。

Harnessなしでの単独導入

Driverの利用にこのリポジトリは要らない:

# このリポジトリからなら一括deploy(任意)
powershell -ExecutionPolicy Bypass -File scripts/deploy-plugin.ps1 -Copy

# 手動でも可: qgis-plugin/qgis_live_driver/ を
# python/plugins/qgis_live_driver/ へコピーし、QGISのプラグイン管理で有効化

あとは WEBENGINE_LIVE_DIR を設定した状態でQGISを起動するだけで、 live dir(<WEBENGINE_LIVE_DIR>/qgis-<pid>/qgis_live_driver/)と レジストリJSONが作られ、上記4系統のいずれでも接続できる (未設定なら何もしない無害なプラグイン)。

セキュリティ: pyeval は任意コード実行。開発専用であり エンドユーザーへの配布物に含めてはいけない(metadata.txtにも Development-only と明記済み)。 HTTPサーバは 127.0.0.1 のみにバインドするが、ローカルマシン上の 任意プロセスからQGIS内部を操作できるためリモート公開は想定しない。 外部公開する場合は必ず 上記手順 でAPIキー認証を有効にし、 QGIS_LIVE_TOOLS で pyeval を含まない最小限のツールに絞ること。
